# 회원가입과 메일 인증

## 관리자 준비

환경설정 → 기본정보 → 메일에서 SMTP, Mailgun 또는 SES 설정과 발신자를 저장합니다. **서비스 주소 (인증 메일 링크)**에는 외부에서 접속할 수 있는 주소(예: `https://reports.example.com`)를 입력하세요. 운영(`DJANGO_DEBUG=false`)에서는 HTTPS 서비스 주소를 사용합니다. 저장된 서비스 주소가 없으면 `DJANGO_ALLOWED_HOSTS`의 명시적인 도메인이 하나일 때 해당 도메인의 HTTPS 주소를 자동으로 사용하며 설정 화면에도 채웁니다. localhost·IP·와일드카드는 추론에 사용하지 않습니다. 도메인이 여러 개이거나 와일드카드만 있다면 대표 서비스 주소를 직접 저장해야 합니다. 운영 인증 링크는 요청의 Host 헤더로 만들지 않습니다. 개발 모드에서는 서비스 주소를 비워 두면 현재 접속 주소를 사용합니다.

기존 테스트 발송 버튼으로 수신을 확인합니다. 회원가입 인증과 관리자 인증 발송은 동일한 저장 설정과 발신자를 사용합니다. Mailgun/SES의 발신자 인증과 샌드박스 수신자 제한도 그대로 적용됩니다.

업데이트 후 `uv sync`, `uv run python manage.py migrate`를 실행합니다. 운영 서버는 `uv run python manage.py collectstatic --noinput` 후 애플리케이션을 재시작하세요. `0021_email_verification`은 인증 상태와 공개 요청 제한 테이블만 추가하며 기존 사용자를 잠그거나 자동 인증하지 않습니다.

## 신규 회원가입

1. 메일 주소와 비밀번호로 가입합니다. 사용자 전용 데모 보고서 생성은 유지됩니다.
2. 인증 안내 화면(`/accounts/email/`)으로 이동합니다. 입력한 메일로 인증 링크를 자동 발송합니다.
3. 메일의 링크를 열고 **메일 인증 완료**를 누릅니다. 메일 미리보기·보안 프로그램의 GET 방문만으로는 인증되지 않습니다.
4. 인증한 계정으로 로그인하거나 이미 로그인한 화면에서 서비스로 이동합니다. 인증 링크는 로그인 자격 증명이 아니며 방문자를 자동 로그인시키지 않습니다.

신규 가입자는 인증 전 보고서·연결·게시판 등 서비스 및 API 이용이 제한됩니다. 로그인·로그아웃·인증 안내·재발송은 가능합니다. 다른 기기에서 인증해도 기존 로그인 세션의 다음 요청부터 이용할 수 있습니다.

발송 설정이나 네트워크 문제가 생겨도 가입 계정과 데모 생성 결과를 유지합니다. 다시 가입하지 말고 로그인해 인증 안내 화면에서 재발송하거나 관리자에게 요청하세요. 로그인한 다른 계정의 인증 링크를 연 경우 로그아웃하고 원래 링크를 다시 열어 주세요.

## 기존 사용자에게 발송

`/admin/auth/user/`에서 사용자를 체크하고 작업 **메일 인증 메일 전송**을 실행합니다. 최대 100명을 선택할 수 있습니다. 결과 화면은 사용자별 요청으로 차례로 처리하며 완료될 때까지 열어 두어야 합니다. 별도 작업자나 예약 작업은 필요하지 않습니다. **발송 중지**는 현재 처리 중인 요청이 끝난 뒤 나머지 요청을 중지합니다.

각 사용자에게 발송 접수·이미 인증 완료·비활성 제외·실패 결과를 표시합니다. 한 사용자의 발송 실패는 다음 사용자 처리를 막지 않습니다. 권한 오류나 네트워크로 결과를 확인할 수 없는 경우 추가 발송을 중지합니다. 메일 주소가 없거나 잘못된 사용자는 주소를 먼저 수정하세요.

사용자 목록에서 **메일 인증** 상태를 확인하고 인증 완료/미인증으로 필터링할 수 있습니다. 상세 화면의 인증 상태와 일시는 읽기 전용입니다. 메일 주소를 변경하면 인증 상태를 초기화하고 이전 링크를 폐기합니다.

기존 사용자와 관리자가 생성한 사용자는 기본적으로 기존 서비스 이용 권한을 유지하며 인증 메일을 발송해도 계정이 잠기지 않습니다. 관리자 계정은 운영 복구를 위해 인증 제한 대상에서 제외됩니다.

## 만료와 발송 제한

- 인증 링크: 24시간, 한 번만 사용. 데이터베이스에는 원문 토큰 대신 SHA-256 해시를 저장합니다.
- 재발송: 60초 간격, 사용자별 시간당 5회 요청. 다시 발송하면 이전 링크를 무효화합니다. 실패한 발송도 요청 제한에 포함합니다.
- 이메일·비밀번호 변경, 사용자 비활성화: 이전 인증 링크를 사용할 수 없습니다. 비밀번호 변경은 이미 완료된 메일 인증을 취소하지 않습니다.
- 공개 가입/재발송: 접속 IP 기준 시간당 20회 요청. IP 원문은 저장하지 않습니다. 시간당 제한 키는 비밀 키 기반 해시이며 오래된 제한 행은 정리합니다.
- 프록시 운영: `REPORT_TRUSTED_PROXIES`에 실제 신뢰 프록시 CIDR만 설정하고 프록시가 X-Forwarded-For를 안전하게 덮어쓰거나 추가하도록 구성하세요. 설정하지 않으면 프록시 주소를 기준으로 공개 요청 제한이 적용될 수 있습니다. 사용자별 발송 제한은 프록시와 무관합니다.

접수 성공은 수신함 도착을 보장하지 않습니다. 받은 편지함과 스팸함에서 확인하세요. API 키·SMTP 비밀번호·공급자 응답 본문은 발송 오류 화면이나 관리자 결과에 표시하지 않습니다.

## 운영 오류 확인

- `https://wrb.writeaday.click`에서 서비스한다면 메일 설정의 서비스 주소를 이 값으로 저장하는 것이 가장 명확합니다. SMTP 접속 정보와 인증 링크 주소는 서로 다른 설정이며 테스트 메일은 링크 주소를 검사하지 않습니다.
- 인증 안내·확인 화면은 `Referrer-Policy: same-origin`을 사용해 HTTPS 폼과 로그아웃의 CSRF 검사를 유지합니다. 토큰이 포함된 최초 링크 응답은 `no-referrer`를 유지합니다. 로그아웃은 CSRF 토큰이 포함된 POST로 실행하세요.
- HTTPS 프록시가 앞에 있다면 실제로 신뢰하는 프록시가 `X-Forwarded-Proto`를 덮어쓰도록 구성한 뒤 `DJANGO_TRUST_PROXY_HEADERS=true`를 사용하세요. 다른 브라우저 출처를 명시적으로 신뢰해야 하는 배포에서만 `DJANGO_CSRF_TRUSTED_ORIGINS`에 정확한 HTTPS 출처를 쉼표로 지정하세요. CSRF 검사는 비활성화하지 않습니다.
- 신규 데모는 DB에 사용자별 연결을 만들고 내장 합성 데이터를 읽으므로 미디어 파일 쓰기 권한이 필요하지 않습니다. 실제 사용자 파일 업로드에는 기존대로 쓰기 권한이 필요합니다. 데모 생성 실패 후에는 인증 완료 후 보고서 라이브러리에서 재시도하거나 관리자의 데모 생성 작업을 사용하세요. 계속 실패한다면 서버 로그의 `Demo report creation failed` 예외를 확인하세요.
